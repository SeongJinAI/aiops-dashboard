# 기능명세서 생성 (nova-feature-spec)

새 기능/API의 **명세서를 코드 작성 전에** 만든다. 이 문서는 사람용이자 **AI가 다음 작업(구현·테스트)에 읽는 컨텍스트**다. 명확하고 검증 가능하게 쓴다.

## 출력 위치

`docs/specs/<기능명>.md` (REPO_ROOT 기준). 이 경로의 `.md`는 Nova 자산 sync로 자동 수집된다.

## 절차

1. 대상 기능의 라우터/서비스/모델을 읽어 현재 상태를 파악한다(있으면). 신규면 사용자에게 핵심 요구사항을 1~2개만 확인한다.
2. 아래 3개 섹션을 **빠짐없이** 채운다.

## 필수 섹션

### 1) API 엔드포인트 명세
표로: `Method | URL | 설명 | 요청(본문/쿼리/헤더) | 응답(성공 shape) | 권한`. 각 필드 타입과 필수 여부 명시.

### 2) 검증 흐름도 (ASCII)
요청 → 인증/인가 → 입력 검증 → 비즈니스 규칙 → 데이터 접근 → 응답의 분기를 ASCII로. 각 실패 분기에 HTTP 상태와 에러코드 표기.
```
요청
 └─ 인증 실패 ──────────► 401 ERR_UNAUTHORIZED
 └─ 입력 검증 실패 ──────► 400 ERR_REQUIRE_*
 └─ 비즈니스 규칙 위반 ──► 409 ERR_ALREADY_EXISTS
 └─ 정상 ───────────────► 200 {...}
```

### 3) 검증 체크리스트
표로: `항목 | 조건 | 실패 시 HTTP | 에러코드(ERR_*)`. 예외 4계층(요청검증 400 / 인증인가 401·403 / 비즈니스 도메인정의 / 인프라 409·500)을 따른다.

## 규칙

- 에러코드는 `ERR_SCREAMING_SNAKE`, 중앙 관리 전제로 명세에 나열(문자열 리터럴 직접 사용 금지 안내).
- 모니터링 전송 기준 메모: 5xx·DB정합성(409)만 전송, 4xx는 미전송.
- 추측 금지 — 불명확하면 "❓ 확인 필요" 마커로 남긴다.
- 완료 후 한 줄 요약과 다음 단계(구현/테스트)를 제시한다.
